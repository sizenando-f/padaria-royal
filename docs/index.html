Padaria Royal

Sistema web full-stack para gestão industrial de panificação, controle de qualidade e Business Intelligence (BI). Registra parâmetros técnicos de cada fornada (ambiente natural ou câmara fria controlada), coleta avaliações sensoriais e utiliza o histórico validado para alimentar um motor preditivo K-NN de sugestão de fermento e um painel analítico de balanço de massa e auditoria climática.

Backend & Motor Analítico
API REST em NestJS 11 com PostgreSQL via Prisma ORM. Autenticação JWT, compressão HTTP Gzip, motor K-NN ponderado, cálculos de BI (balanço de massa, Zona de Ouro e Run-Rate) e rotinas agendadas com @nestjs/schedule.
Frontend Mobile-First
Interface em Next.js 16 (App Router), React 19, TypeScript e Tailwind CSS 4. Cache e sincronização de estado assíncrono com TanStack React Query, gráficos interativos em Recharts e responsividade otimizada para uso no chão de fábrica.
Banco de Dados & Cloud
PostgreSQL 15 gerenciado pelo Prisma ORM (local via Docker Compose e em produção via Neon Serverless Postgres). Deploy contínuo distribuído entre Vercel (Frontend) e Render (Backend API).
Integrações & Resiliência
Previsão meteorológica via Open-Meteo com arquitetura de fallback híbrido (Backend + Client-side) e automação de backups diários em CSV via Resend API com retry exponencial e trava de concorrência.

Lógica Central

Algoritmo de Sugestão de Fermento (K-NN Ponderado)

O módulo de sugestão responde a uma pergunta prática: dado o clima previsto e o tempo de fermentação desejado em armário aberto, qual deve ser a dosagem de fermento por quilo de farinha? A abordagem utiliza um algoritmo K-Nearest Neighbors (K-NN) ponderado pelo inverso da distância de Manhattan sobre o histórico de fornadas bem-sucedidas, sem necessidade de treinamento offline.

Etapa 1 — Seleção e sanitização da base histórica

Apenas fornadas que atendam simultaneamente aos quatro critérios abaixo entram no espaço de busca:

  • Nota da avaliação ≥ 4 (Bom ou Excelente)
  • Campo tempAmbienteInicial preenchido
  • Campo tempAmbienteFinal preenchido
  • Fermentação natural (usouCamara: false) — fornadas de Câmara Fria são estritamente excluídas
Isolamento de Câmara Fria no K-NN
Fornadas realizadas em câmara fria seguem parâmetros padronizados de ambiente fechado (6°C ➜ 30°C, 8h de fermentação, 20 kg de trigo, 110 g de fermento e 80 ml de emulsificante). Excluí-las da busca K-NN impede que clusters artificiais ou registros salvos com temperatura externa contaminem os 20 vizinhos mais próximos das fornadas naturais.

Etapa 2 — Cálculo de distância (Manhattan Normalizada)

Para cada fornada histórica elegível, calcula-se a distância multidimensional em relação ao cenário atual, combinando desvios térmicos e diferença temporal:

distancia = |tempInihist − tempIniatual|
          + |tempFimhist − tempFimatual|
          + |tempohist − tempoalvo| ÷ 60

// A divisão por 60 converte minutos para horas, equiparando a escala temporal // à escala de graus Celsius (1 hora de diferença equivale a 1°C de distância).

Os registros históricos são ordenados de forma crescente pela distância e os K = 20 vizinhos mais próximos são selecionados para a inferência.

Etapa 3 — Peso inversamente proporcional

Cada uma das 20 fornadas selecionadas recebe um peso que cresce exponencialmente quanto mais próxima ela estiver do cenário atual:

peso = 1 ÷ (distancia + 0.1)

// A constante de suavização +0.1 evita divisão por zero quando a distância é 0 // (temperatura e tempo idênticos ao alvo). Nesse caso, peso máximo = 10.

Etapa 4 — Média ponderada da proporção fermento/farinha

O algoritmo opera sobre a densidade relativa (gramas de fermento por quilo de farinha) de cada fornada, tornando a recomendação invariante à escala da batida:

proporcaoi = fermentoi ÷ farinhai

proporcao_media = Σ(proporcaoi × pesoi) ÷ Σ(pesoi)

fermento_sugerido = round(proporcao_media × farinha_atual)

A resposta sempre inclui as 5 fornadas mais próximas usadas no cálculo (campo provas), com todos os seus parâmetros. Isso permite que o gerente ou padeiro inspecione a origem da recomendação e julgue sua pertinência.
Análise Industrial

Inteligência de Produção (BI Gerencial)

Exclusivo para o perfil de gerência no Dashboard, o módulo de Business Intelligence (GET /producao/bi-stats) transforma os dados operacionais do chão de fábrica em indicadores físicos, termodinâmicos e preditivos.

1. Balanço de Massa Físico (3 Cenários de Rendimento)

Modelado sobre a receita industrial padrão da padaria — 40 kg de farinha + 20 kg de água (50% de hidratação) + 0,2 kg de aditivos = 60,2 kg de massa crua, resultando em 46,75 kg de pão assado (unidades de 55g) após a perda térmica de cocção —, o sistema calcula a produção estimada sob três perspectivas:

// Aba 1 — Por Farinha (Rendimento Direto: 21,25 pães por kg de trigo)
paes_farinha = round(totalFarinhaKg × 21.25)

// Aba 2 — Massa Crua (Fator de hidratação 1,505× e 14 pães de ~71g por kg de massa)
massa_crua_kg = totalFarinhaKg × 1.505
paes_massa_crua = round(massa_crua_kg × 14)

// Aba 3 — Pão Assado (Quebra térmica de 22,3% na cocção → fator 1,16875× e 18 pães de 55g/kg)
massa_assada_kg = totalFarinhaKg × 1.16875
perda_termica_kg = massa_crua_kg − massa_assada_kg
paes_assados = round(massa_assada_kg × 18)

2. Auditoria Climática de Dosagem (Zona de Ouro ±10%)

Avalia a precisão da dosagem de fermento aplicada pelos padeiros frente às condições térmicas naturais (excluindo fornadas de câmara fria). O histórico é segmentado pela temperatura média da fornada em três faixas:

  • Frio (< 20°C): exige maior concentração de fermento para compensar a letargia biológica.
  • Ameno (20°C – 26°C): faixa de equilíbrio operacional.
  • Quente (> 26°C): exige redução de fermento para evitar superfermentação e queda de estrutura.

Para cada faixa, o motor extrai a proporção ideal (g/kg) a partir das fornadas com Nota 5 (Excelente). Se o filtro mensal não possuir amostras Nota 5 em determinada faixa climática, o algoritmo aciona automaticamente um fallback histórico global (sinalizado na interface com a badge Ref. Histórica). Uma fornada é classificada como Aderente (Zona de Ouro) quando sua dosagem fica dentro da margem de tolerância de ±10% do ideal daquela faixa.

3. Sensibilidade e Estabilidade Térmica (ΔT)

Mede o impacto da amplitude térmica durante a fermentação (ΔT = |tempFinal − tempInicial|) sobre a qualidade final do pão, comparando a nota média e a taxa de excelência entre fornadas em Ambiente Estável (ΔT ≤ 4°C) e fornadas submetidas a Alta Oscilação (ΔT > 4°C).

4. Projeção Mensal de Consumo (Run-Rate)

No filtro mensal (Neste Mês) ou no último mês da série histórica, o gráfico empilhado projeta o fechamento de consumo de farinha calculando o ritmo diário médio (farinhaAcumulada ÷ diaAtualDoMes) multiplicado pelo total de dias do mês corrente.

Lógica do Sistema

Regras de Negócio

Detecção híbrida de Câmara Fria

Uma produção pode ser marcada como realizada em câmara fria (usouCamara = true) de duas maneiras complementares:

  • Acionamento explícito (Switch no Frontend): Na tela de Nova Produção, ativar a chave Câmara Fria preenche instantaneamente os valores padrão (18:00 às 02:00, 8h, 6°C inicial, 30°C final, 20 kg de trigo, 110 g de fermento e 80 ml de emulsificante), mantendo-os editáveis e desativando o botão de sugestão K-NN.
  • Detecção automática por expressão regular (Backend): Ao criar/editar uma produção, submeter uma avaliação ou importar planilhas CSV legadas, o backend inspeciona os campos observacoes e comentario. Qualquer menção textual a variantes como "câmara fria", "camara" ou "câmera fria" (independente de acentuação ou maiúsculas) converte automaticamente o registro para usouCamara = true.

Janela de edição de 3 dias

Padeiros podem editar produções e avaliações somente se a produção vinculada tem menos de 3 dias a partir de horaInicio. O cálculo é feito em milissegundos:

const diferencaMs = Date.now() - new Date(producao.horaInicio).getTime();
const diferencaDias = diferencaMs / (1000 * 60 * 60 * 24);
if (diferencaDias > 3) throw UnauthorizedException();

Gerentes não têm essa restrição.

Restrição de horário de login

Ao fazer login, o backend compara o horário atual (no fuso do Brasil) com os campos horarioEntrada e horarioSaida do usuário. A comparação é feita entre strings no formato HH:MM, o que é funcionalmente correto para verificar se o horário atual está dentro do intervalo permitido.

Unicidade da avaliação

Antes de criar uma avaliação, o service verifica se já existe um registro com o mesmo producaoId. Como o campo possui constraint @unique no schema, a proteção existe tanto na camada de aplicação quanto no banco de dados.

Autoexclusão bloqueada

Um gerente não pode excluir sua própria conta via DELETE /usuario/:id. O controller compara o id do parâmetro com req.user.sub (ID extraído do token JWT).

Log de auditoria em exclusões

Toda chamada a DELETE /producao/:id cria um registro em LogExclusao antes de executar a deleção, preservando o histórico mesmo que o registro de produção deixe de existir.

Sistema de Permissões

Cada usuário possui 5 permissões booleanas independentes armazenadas no banco. Ao fazer login, essas permissões são emitidas no payload do JWT e também devolvidas no corpo da resposta para uso imediato pelo frontend.

Aplicação dupla
As permissões são verificadas no backend (antes de executar a operação) e usadas no frontend para esconder ou desabilitar elementos de interface. Gerentes ignoram as permissões individuais e têm acesso irrestrito a todos os recursos.

Fluxos

Ciclo de Vida de uma Produção

1
Registro da fornada (Natural ou Câmara Fria)
O padeiro escolhe o método de fermentação. Em modo natural, o frontend consulta GET /producao/clima-previsao (com fallback client-side) para preencher as temperaturas automaticamente. Se o switch Câmara Fria for ativado, o sistema preenche a receita padrão (18:00➜02:00, 6°C➜30°C, 20kg trigo, 110g fermento, 80ml emulsificante). POST /producao calcula tempoFermentacaoMinutos e persiste o registro.
2
Estado pendente
A fornada existe no banco sem avaliação. GET /producao/pendentes a retorna. O dashboard exibe o contador de pendências e alerta visual.
3
Avaliação sensorial
O operador atribui uma nota de 1 a 5, com comentário e temperatura final real opcional. POST /avaliacao verifica unicidade, detecta eventuais menções textuais à câmara fria no comentário e persiste. A fornada sai da lista de pendentes.
4
Contribuição ao modelo K-NN e ao BI
Todas as fornadas alimentam imediatamente o Balanço de Massa do BI. Já as fornadas naturais (usouCamara: false) com nota ≥ 4 e temperaturas preenchidas passam a integrar a base de vizinhos do algoritmo K-NN e a Auditoria Climática (Zona de Ouro).

Fluxo de Sugestão Inteligente

1
Frontend busca previsão climática
Ao informar os horários de início e fim em fermentação natural, o frontend chama GET /producao/clima-previsao (ou consulta a Open-Meteo diretamente do navegador em caso de rate-limit no servidor). As temperaturas são preenchidas automaticamente nos campos do formulário.
2
Requisição de sugestão
Com farinha, temperaturas e tempo de fermentação preenchidos, o frontend chama GET /producao/sugestao?farinha=20&temp=24&tempFim=26&minutos=180.
3
Cálculo K-NN no backend
O algoritmo filtra apenas fornadas naturais bem-avaliadas, seleciona os 20 registros mais similares pela distância de Manhattan normalizada, aplica os pesos inversamente proporcionais e retorna a dosagem sugerida em gramas junto com as 5 fornadas mais próximas como evidência.
4
Exibição e decisão
O padeiro vê a sugestão e pode aceitar, ajustar ou ignorar. O valor pode ser editado livremente antes de submeter o formulário.

Backup Automático e Resiliência

O BackupModule usa @nestjs/schedule para executar uma rotina diária às 19:00 (fuso horário America/Campo_Grande), além de permitir disparo manual via POST /backup/run. O processo conta com mecanismos de proteção contra falhas de rede:

1
Trava de concorrência e idempotência
O service verifica as flags em memória isProcessing e lastBackupDate para impedir execuções duplicadas no mesmo dia ou disparos simultâneos.
2
Resolução do destinatário e geração do CSV
Busca o e-mail configurado na tabela Configuracao pela chave EMAIL_BACKUP (com fallback para a variável de ambiente EMAIL_DESTINO) e gera o CSV completo via ProducaoService.exportarDados().
3
Envio via Resend API com Retry Exponencial
Envia o CSV em anexo utilizando a API HTTP da Resend (RESEND_API_KEY). Em caso de instabilidade externa, executa até 5 tentativas com exponential backoff (2s, 4s, 8s, 16s...).

O e-mail destinatário pode ser alterado a qualquer momento pelo gerente no Painel Admin via PATCH /admin/config/email.

Gerenciamento de Sessão e Estado Assíncrono

A sessão é controlada pelo AuthContext (disponível via AuthProvider no layout.tsx), enquanto o estado de servidor e cache de dados analíticos são gerenciados pelo TanStack React Query (QueryProvider).

Cache e Sincronização (React Query)

Consultas pesadas — como estatísticas do Dashboard, BI Gerencial (['bi-stats', periodo]) e listagens do histórico — são cacheadas em memória, evitando requisições redundantes ao alternar abas ou filtros e garantindo invalidação automática após mutações.

Persistência de Sessão

Ao fazer login, o token JWT é armazenado em localStorage com a chave royal_token. Os dados básicos do usuário (nome, cargo, permissões) são armazenados em royal_user como JSON. Na inicialização do app, o AuthProvider verifica a presença dessas chaves e restaura a sessão automaticamente.

Proteção de rotas e Expiração

O useEffect do AuthProvider redireciona para /login caso nenhum token seja encontrado no localStorage. Rotas administrativas (/usuarios e /painel) verificam adicionalmente o cargo via isGerente. Quando o backend retorna 401 em qualquer requisição, o interceptor executa logout() e redireciona para /login.

Infraestrutura de Produção
Em produção, o sistema opera de forma distribuída: Frontend hospedado na Vercel, Backend API na Render (com compressão HTTP Gzip ativa) e banco de dados PostgreSQL serverless na Neon. O fluxo de branches segue GitFlow simplificado (feature/* ➜ develop ➜ main).

cd backend

cp .env.example .env

npx prisma migrate deploy

# Popular com dados iniciais (seed)
npx prisma db seed

# Iniciar em modo de desenvolvimento
npm run start:dev

A API estará disponível em http://localhost:3000.

cd frontend
npm install
npm run dev

A interface estará disponível em http://localhost:3001 (ou 3000 caso o backend esteja em outra porta).
